What We Did — Project Explanation
🎯 The Aim
"Prove that Kubernetes workloads are over-provisioned, measure the waste, optimize them, and show the cost reduction using real monitoring tools."

In Kubernetes, every pod declares how much CPU and memory it requests (guaranteed reservation). The problem is developers often set these numbers too high "just to be safe." The cluster holds that resource aside — even if the pod never uses it. In cloud environments, you pay for that reserved space whether it's used or not.

Our goal was to demonstrate this problem end-to-end and fix it with data.

🔧 Tools We Used and Why
Tool	What it is	Why we used it
Minikube	A local single-node Kubernetes cluster that runs inside Docker	We can't afford real cloud nodes, so Minikube simulates a production Kubernetes environment on your laptop
kubectl	The command-line tool to control Kubernetes	Used to deploy pods, check status, check resource usage (kubectl top)
Helm	A package manager for Kubernetes (like apt/pip but for K8s apps)	Used to install complex monitoring tools (Prometheus + Grafana) in one command instead of writing hundreds of YAML lines manually
Prometheus	A metrics database that scrapes and stores all cluster statistics every 15 seconds	Collects CPU usage, memory usage, pod counts, node stats — the raw data source for everything else
Grafana	A dashboard tool that visualizes data from Prometheus	Lets us see beautiful graphs of CPU usage, memory usage, efficiency ratios over time
OpenCost	A Kubernetes cost allocation engine	Converts CPU/memory usage into estimated dollar costs per namespace/pod using a pricing model (AWS rates)
GitHub Actions	CI/CD automation platform	Automatically validates all our Kubernetes YAML files and shell scripts every time we push code
Docker Desktop + WSL2	Container runtime + Linux environment on Windows	Minikube needs Linux and Docker — WSL2 gives us Ubuntu on Windows, Docker Desktop provides the container engine
📦 What We Actually Built
We deployed 3 fake microservices inside Kubernetes, each intentionally given way more resources than they need:

Service	What it does	CPU Requested	CPU Actually Used
api-service	An nginx web server that handles HTTP requests	500m	1m
background-worker	Polls the API and does CPU arithmetic (simulates a processing job)	1000m	82m
report-service	Another nginx server (the most over-provisioned)	2000m	1m
2000m means 2 full CPU cores reserved. It used just 1 millicores (0.001 cores) — a 99.95% waste.

🔬 How We Achieved the Aim — Step by Step
Step 1 — Deploy the over-provisioned workloads We deployed all 3 services with bloated resource requests. At this point the cluster is "wasting" 3500m of CPU reservations.

Step 2 — Set up monitoring We installed Prometheus (collects all metrics) and Grafana (shows them visually). The Grafana dashboard we built shows:

CPU usage per pod over time
Bar charts of requested vs actually used
Efficiency gauges (how much of what you reserved are you actually using)
Step 3 — Install OpenCost OpenCost reads from Prometheus and calculates: "If this cluster were running on AWS, how much would these resource reservations cost per hour?" It gave us the baseline cost: $0.1195/hr for our cost-demo namespace.

Step 4 — Run a load test We ran a script that fired HTTP requests at our services for 120 seconds, simulating real traffic. This is important — it means the CPU numbers we measured are under realistic load, not an idle system.

Step 5 — Measure actual usage While the load ran, we used kubectl top pods to see real CPU/memory numbers. We recorded these in results/baseline.csv.

Step 6 — Calculate right-sized values Using the formula: optimized request = peak observed usage × 1.3 (we add 30% safety headroom above the measured peak):

api-service: used 1m → set to 5m
background-worker: used 82m → set to 110m
report-service: used 1m → set to 5m
Step 7 — Apply the optimization We applied the new smaller resource requests. Kubernetes did a rolling update — the old pods were replaced one by one with no downtime.

Step 8 — Measure again Ran the same load test. Used OpenCost API to get the after cost: $0.0006/hr.

📊 What We Proved
What we measured	Before	After	Result
Total CPU Reserved	3500m	120m	↓ 96.6%
Total Memory Reserved	3.5Gi	72Mi	↓ 98%
Estimated Cost/hr	$0.1195	$0.0006	↓ 99.5%
Cluster Efficiency	3.5%	8.7%	↑ improved
💡 The Core Insight (What to Say in Your Viva)
"In Kubernetes, you pay for what you reserve — not what you use. A pod requesting 2000m CPU costs the same as one actually using 2000m. By measuring real utilization under load and right-sizing requests to peak × 1.3, we eliminated 96.6% of wasted CPU reservations and reduced the estimated namespace cost by 99.5% with zero downtime."

⚠️ Important Caveat to Always Mention
The cost numbers ($0.12/hr, $0.0006/hr) are estimates based on AWS pricing rates fed into OpenCost. We're running on a local laptop — there is no real AWS bill. But the resource reduction percentages (96.6%, 98%) are 100% real — those come directly from kubectl top and the Kubernetes API.
