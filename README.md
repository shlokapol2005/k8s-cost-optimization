# Kubernetes Cost Monitoring & Resource Optimization

> **Research Question:** How can Kubernetes resource requests and limits be optimized to reduce estimated infrastructure cost while maintaining application performance?

---

## Architecture

```
                         GitHub
                           │
                           ▼
                    GitHub Actions
                  YAML + Shell Validation
                           │
                           ▼
                     ┌───────────┐
                     │ Minikube  │
                     │ Kubernetes│
                     └─────┬─────┘
                           │
             ┌───────────┼────────────┐
             ▼             ▼              ▼
           API           Worker         Report
           Pod             Pod            Pod
             │       polls ↑              │
             └───────────┘              │
             ↑                            │
       Load Generator                     │
             │ HTTP traffic               │
             └───────────────────────────┘
                           │
                  ┌────────┤─────────┐
                  ▼                 ▼
             Prometheus          OpenCost
                  │                 │
                  └────────┬────────┘
                           ▼
                        Grafana
                           │
             ┌───────────┼───────────┐
             ▼             ▼             ▼
          CPU/Memory     Allocation     Cost
          Dashboard      Dashboard     Dashboard
                           │
                           ▼
                  Optimization Analysis
                           │
                     ┌─────┤─────┐
                     ▼           ▼
                  BEFORE       AFTER
                  Metrics      Metrics
                     └─────┬─────┘
                           ▼
                    Cost Reduction /
                 Resource Optimization
```

> **Load chain:** Load Generator → `api-service` (HTTP) → `background-worker` polls `/work` endpoint → does CPU arithmetic. This means the worker's measured utilization is driven by real traffic, not an idle loop.

## Optimized Workloads (After Optimization)

> ⚠️ **These values are NOT predetermined.** The `k8s/optimized-deployments.yaml` file
> contains `REPLACE_AFTER_MEASUREMENT` placeholders. You fill these in after running
> `kubectl top pods` during the baseline load test, using the formula:
> `request = peak_observed_usage × 1.3`, `limit = request × 2`.
>
> Your actual numbers determine the result — that is the experiment.

| Workload | CPU Request | Memory Request |
|----------|------------|----------------|
| `api-service` | *measured × 1.3* | *measured × 1.3* |
| `background-worker` | *measured × 1.3* | *measured × 1.3* |
| `report-service` ✅ | *measured × 1.3* | *measured × 1.3* |

## Step-by-Step Setup Guide

> See [SETUP_GUIDE.md](SETUP_GUIDE.md) for the complete installation walkthrough.

### Quick Start (WSL2)

```bash
# 1. Clone the repo
git clone <your-repo-url>
cd k8s-cost-optimization

# 2. Start Minikube (6 CPUs, 8 Gi RAM)
minikube start --cpus=6 --memory=8192 --driver=docker
minikube addons enable metrics-server

# 3. Deploy baseline workloads
kubectl apply -f k8s/

# 4. Install monitoring stack
bash scripts/setup.sh --skip-monitoring=false

# 5. Run load test and collect baseline
bash load-testing/load-test.sh medium
bash scripts/collect-baseline.sh

# 6. Edit optimized values based on your measurements
nano k8s/optimized-deployments.yaml   # replace REPLACE_AFTER_MEASUREMENT

# 7. Apply optimized config
kubectl apply -f k8s/optimized-deployments.yaml

# 8. Run same load test and collect after
bash load-testing/load-test.sh medium
bash scripts/collect-after.sh
```

## Grafana Dashboard

1. Open Grafana: `http://<minikube-ip>:32000`
2. Login: `admin / devops-demo-2024`
3. Go to **Dashboards → Import → Upload JSON file**
4. Select `monitoring/grafana/dashboard.json`
5. Set datasource → **Prometheus**

Dashboard sections:
- **Resource Overview** — CPU & Memory timeseries per pod
- **Requests vs Usage** — Bar charts comparing requested vs actual
- **OpenCost Cost Panels** — Estimated cost per pod, CPU vs Memory split
- **Efficiency Gauges** — Red/Yellow/Green ratio of used/requested

### Access OpenCost

```bash
# Find Prometheus service name first:
kubectl get svc -n monitoring | grep prometheus

# Port-forward both ports:
kubectl port-forward svc/opencost -n opencost 9090:9090 9003:9003
# UI  → http://localhost:9090
# API → http://localhost:9003
```

Tabs to show during demo:
- **Overview** — Namespace-level cost
- **Allocation** — Cost per workload/pod
- **Assets** — Node-level resource costs

## Conclusion

This project demonstrates:
1. How to instrument a Kubernetes cluster with **cost-aware observability**
2. How to identify **over-provisioned workloads** using real utilization data
3. How to apply **right-sized resource requests** based on empirical measurements
4. How to **quantify the cost impact** of optimization using OpenCost estimates
